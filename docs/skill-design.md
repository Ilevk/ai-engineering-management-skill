# 스킬 설계와 인터뷰 기록

상태: 2026-10-05 초기 개정본의 허구 사례 독립 행동 검증과 두 유저 레벨 스킬의 초기 설치·readback 검증 완료.

이번 추가 개정(티켓 기반 GitHub 조사, 초안 기본 템플릿, 확인 질문의 컨텍스트 토글)은 스킬 형식·YAML·자체 참조 경로를 검증했다. 실제 커넥터 연동 조사와 설치본 갱신은 이번 작업 범위에 포함하지 않았다.

## 목표와 범위

두 스킬을 별도 폴더로 관리하고, 완성 후 유저 레벨 스킬로 설치한다.

1. `quarterly-member-review`: 주어진 팀의 팀원별 분기 평가서 작성
2. `review-meeting-prep`: 작성된 평가서를 바탕으로 면담 준비

팀 평가서는 이번 범위에서 제외한다.

## 확정된 입력과 책임

- 대상 팀과 팀원은 실행하는 매니저가 제공한다.
- 레벨별 요구사항과 평가에 사용할 자료는 매니저가 제공한다.
- 자료는 직접 제공하거나 실행 환경에 정의된 커넥터와 MCP를 통해 조회한다.
- 특정 제품, 자료 종류, 평가 기준이나 공통 양식을 스킬에서 제안하거나 강제하지 않는다.
- 팀장이 개인 평가서를 작성하고 중간 검토한다.
- HR, CTO와 CEO가 최종 결과를 확인한다.
- 결과물의 주 용도는 공식 제출용 평가서다. 같은 평가서를 면담 준비에 사용할 수 있다.
- 점수는 인간 매니저가 판단한다. 스킬은 점수와 등급을 산정하거나 추천하지 않는다.

## 실행 요청

- “지난 N 분기의 팀원 평가를 시작하고 싶다.”
- “이번 분기의 팀원 평가를 해야한다.”

실행 시 정확한 날짜 범위를 제안하고 확인받는다. 연도와 분기 기준, 월말, 필요한 시간대와 종료 경계를 확인한다. “지난 N 분기”가 특정 분기인지 여러 분기인지 모호하면 날짜 범위와 해석을 함께 확인한다.

## 평가서 작성 흐름

1. 조사 착수
   - 정확한 기간, 대상자와 제공받은 데이터 소스를 매니저에게 확인한다.
   - 데이터 소스별 서브 에이전트가 실제 소스와 내용을 탐색한다. 제공된 경우 Jira project, Notion 내용과 관련 하위 자료, Slack 채널명을 다시 제시한다.
   - 팀의 연간 또는 분기 목표를 요청한다.
   - 팀원의 현재 레벨을 제공받고 회사나 팀의 Job Level 정의를 사용한다. 정의가 없으면 매니저와 현재 및 다음 수준의 기대치를 논의하고 확인한 뒤 진행한다.
2. 위임 조사와 반복 교차검증
   - 메인은 원문 수집, 그룹핑, 초안 작성과 직접 사실 검증 없이 배정·진행 상태·인간 gate·검증 결과 취합·수정 재배정만 한다.
   - 착수 소스 탐색, 수집, 수집 검증, 그룹핑, 그룹핑 검증, 초안과 초안 검증은 별도 역할에 배정한다. 작성자 재독은 독립 검증이 아니다.
   - 실행 환경의 latest fast-tier가 확인된 범위의 원문을 로컬 임시 파일에 모두 수집한다. latest top-tier가 목표별로 그룹핑하고, 별도의 latest top-tier가 초안을 작성한다. 역할별 실제 모델명과 상태를 기록한다.
   - 소스별 날짜 기준, identity/alias와 collaborator 매칭 규칙을 착수 때 확인한다. Jira 예시에서는 Assignee 또는 collaborator의 모든 티켓과 본문·메타데이터·모든 코멘트를 월별로 수집한다. 티켓 및 코멘트 pagination, 각 코멘트 원문·작성자·시각·실제 링크/source ID와 누락을 추적한다.
   - 코드베이스 확인이 필요한 경우 Jira 등 업무 관리 도구의 티켓을 출발점으로 GitHub 조사를 수집 역할에 배정한다. 연동 정보나 PR·커밋 링크를 따라 실제 diff·관련 코드를 확인하며, 직접 링크가 없으면 허용된 저장소 안에서 티켓 key·식별자로 검색해 업무 내용을 대조한다. GitHub 조회 범위가 미확정이면 매니저에게 확인하고 티켓–PR–커밋 관계, 커밋 SHA·코드 위치, 개인 역할·기간과 조회 누락을 독립 검증한다. 평가서 작성과 면담 준비의 추가 조사에 동일하게 적용한다.
   - Slack 언급 전체와 업무 문맥, Notion Tech Spec/ADR/Meeting Notes, Google Docs Gemini 회의 노트 등은 제공된 도구의 예시다. Linear/Teams/Obsidian 등 같은 범주의 도구를 사용할 수 있으며 특정 제품을 요구하지 않는다.
   - 원문을 요약으로 대체하지 않는다. 페이지/커서 순서, 범위, 건수, 실패와 불가 항목을 manifest로 추적하고 부분 수집을 완료로 보고하지 않는다. 개인정보 원문을 공개 스킬 저장소에 넣지 않는다.
   - 그룹핑은 팀 연간·분기 목표별 주요 기여를 추리되 업무 흐름과 개인 역할·기여 세부사항을 유지한다. 억지 목표 귀속, 팀 성과의 개인 귀속, 중복과 자료 부재의 역량 미달 변환을 금지한다.
   - 주요 중간 단계의 독립 검증 지적을 작성자에게 재배정하고 재검증한다. 도구·tier·독립 에이전트 부재는 인간에게 보고하고 변경 허용 없이 우회하지 않는다.
   - 착수 이후 범위 안의 조사 진행에는 매니저의 단계별 확인을 요구하지 않는다.
   - 확인되지 않거나 충돌하는 내용은 평가 근거에서 제외한다. 초안은 계속 작성하고 실제 확인한 근거 링크와 확인 질문을 매니저에게 제시한다.
3. Markdown 초안
   - 개인별 MD 파일에 업무와 근거, 현재 기대치와의 관계 및 다음 수준에 필요한 역량의 참고 코멘트를 작성한다.
   - 초안의 기본 템플릿은 `성과`, `역량`, `기술기여` 세 항목이며, 각 항목에서 확인된 사실·근거, 서술형 참고평가와 확인 질문을 구분한다. `성과`는 업무 결과와 개인 기여를 팀 목표에 연결해 평가하고, `기술기여`는 설계·구현·리뷰 등 확인된 기술 기여와 개인의 역할을 평가한다.
   - `역량` 항목에는 확인된 행동·개인 기여와 제공된 Job Level 요구사항을 근거로 역량 측면의 서술형 참고평가를 작성한다. 역량 이름이나 관련 활동을 나열하는 데 그치지 않고 현재 기대 수준의 충족 여부와 성장에 필요한 부분을 근거로 설명한다.
   - 각 매니저 확인 질문 아래에는 실제 조사한 컨텍스트를 토글로 제공한다. 업무 배경·진행 흐름과 시점, 개인 역할·협업, 확인된 사실, 미확인·충돌 사항과 질문 이유, 실제 근거 링크 및 답변이 평가에 미치는 영향을 담아 매니저가 열어보고 참고 후 답변하도록 안내한다. Markdown은 `<details>`를, Notion에 질문을 포함할 때는 실제 toggle 블록을 사용하고 별도 검증 역할이 원문과 대조한다. 면담 준비의 확인 질문에도 적용한다.
   - 매니저가 별도 초안 구성을 지정하면 기본 템플릿보다 우선한다. 기본 템플릿은 평가 기준이나 공식 제출 양식을 정의하지 않으며, 최종 포맷은 매니저가 제공한다.
   - 매니저가 항목별로 실제 있었던 일인지 확인하고 직접 수정하거나 인터뷰로 정정한다.
   - 서술형 참고 의견을 제안할 수 있으나 실제 판단은 인간 매니저가 한다.
   - 직접 수정한 파일을 다시 읽고 변경을 보존한다.
4. 최종본
   - 검토 완료된 초안을 매니저가 제공한 최종 포맷으로 작성한다.
   - private Notion 데이터베이스나 문서 시스템을 선택적으로 권장하며 거절하면 넘어간다.
   - 실제 저장은 지정한 위치와 권한 범위에 따라 수행하고 다시 읽어 확인한다.

## outer loop와 장기 메모리

- 변경 전 초안과 매니저의 수정, 변경 이유를 해당 회차에서 비교하고 반영한다.
- 장기 메모리에는 매니저의 작성 선호와 면담 순서만 저장한다.
- 개인별 사실 정정, 평가 판단과 실적은 해당 회차 기록으로 남긴다.
- 로컬 또는 리모트 메모리 위치는 실제 실행 환경에서 매니저가 지정한다.
- 다음 회차에는 관련 선호를 읽되 새 요청, 원문 사실과 해당 회차의 요구사항을 우선한다.

## 면담 준비 결과물과 흐름

- 두 스킬에 동일한 메인 오케스트레이션 전용 원칙을 적용한다. 면담 입력 확인과 추가자료 확인은 위임하며 추가 원문 수집은 latest fast-tier, 면담 준비·해석·성장 제안과 피드백 최종본 반영은 latest top-tier 역할이 맡는다. 작성자와 별도 latest top-tier가 원문 기반 독립 검증과 수정 후 재검증을 수행한다.
- 메인은 원문 직접 읽기·평가 분석·작성·수정·사실 검증·메모리 쓰기를 대신하지 않는다. 작성 선호·면담 순서 메모리 기록 및 실제 저장·readback도 서브에 배정하며 개인 자료 제외와 실제 환경의 쓰기 규칙을 따른다.
- 이미 확정된 매니저 입력은 재승인하지 않는다. 런타임 지원 모델 목록 또는 tier로 선택하고 실제 모델명과 최신 여부의 확인 한계를 기록한다. 독립 서브·필요 도구·모델이 없으면 인간에게 보고하고 변경 허용 없이 우회하지 않는다.

- 팀원 대상: 현재 Job Level의 기대치 달성 여부, 다음 Job Level에 필요한 노력과 입증할 역량.
- 매니저 대상: 팀원에게 제안할 성장 방향, 매니저의 지원 과제와 상위 매니저와 논의할 사항.
- 매니저별 면담 순서를 먼저 묻고 장기 메모리에 기록한다.
- 별도 순서가 없으면 최종 평가서 전달 → 1주일 이내 1 on 1 → 피드백과 이의의 최종본 반영 → 최종 평가서 제출 순서를 사용한다.
- 실제 전달, 미팅과 제출은 현재 요청에서 허용한 경우에 수행한다. 준비 단계에서 완료된 것으로 기록하지 않는다.

## 작성 원칙

- 확정한 규칙은 스킬 본문에 반영한다.
- 미확정 사항은 인터뷰 질문으로 유지하고 임의의 절차로 메우지 않는다.
- 팀이나 개인의 실제 평가 자료를 이 저장소에 넣지 않는다.
- 실행 환경에서 사용 가능한 도구를 확인하되, 접근 가능한 모든 자료를 평가 입력으로 간주하지 않는다.
- 스킬 이름은 현재 작업명이며 내용이 확정되면 조정할 수 있다.

## 준비와 검증 계획

1. 지정한 빈 GitHub 저장소를 `~/Desktop/dev/ai-engineering-management-skill`에 복제한다.
2. 두 스킬, 표시 정보와 인터뷰 기록을 로컬에 작성한다.
3. 두 스킬의 형식, 독립 설치 가능 여부와 미확정 사항 표기를 확인한다.
4. 인터뷰를 이어가며 작성 절차를 구체화한다.
5. 절차가 확정되면 실제 요청 예시로 동작을 확인하고 유저 레벨 경로에 설치한다.

로컬 검증과 유저 레벨 설치까지 진행한다. 커밋과 원격 push는 이번 단계에 포함하지 않는다. 실제 평가 자료 조회, 실제 평가서 작성과 외부 제출도 범위에 포함하지 않는다.

## 작업 근거

- 제작 지침: `skill-creator/SKILL.md`, `skill-creator/references/openai_yaml.md`
- 한국어 문구 지침: `ko-prose/SKILL.md`
- 시작 환경의 `ai-center/AGENTS.md`, `ai-center/.agents/docs/agent-workflow-reference.md`와 artifact policy를 확인했다.
- 대상은 ai-center 밖의 새 독립 저장소이므로 서브모듈 동기화, ai-center의 Jira/PR/CI 절차는 적용하지 않는다.
- 변경은 스킬과 참조 문서에 한정한다. 별도 코드 피어 리뷰, 저장소 CI와 실제 커넥터 통합 검증은 실행하지 않는다. 대신 스킬 형식과 참조를 확인하고 가상 사례에서 독립 에이전트가 작성 절차를 실행하도록 검증한다.

## 초기 준비 단계 검증

- 두 스킬에 `skill-creator/scripts/quick_validate.py`를 실행했고 모두 `Skill is valid!`로 통과했다.
- 표시 정보 YAML, 프롬프트의 스킬 이름, 로컬 문서 링크, 미완성 scaffold와 공백을 확인했다.
- 스킬 폴더 밖의 파일을 필수 참조로 사용하는 지침은 없다.
- 초기 형식 검증은 절차가 미확정이던 준비 초안에 대한 결과다. 이번 인터뷰 반영본의 검증은 아래에 별도로 기록한다.

## 인터뷰 반영본 검증
