# 분기 팀원 평가서 작성

주어진 팀의 팀원별 공식 제출용 평가서를 작성한다. 팀장이 작성과 중간 검토를 맡고 HR, CTO와 CEO가 최종 결과를 확인한다. 팀 평가서는 제외한다.

평가 기준, Job Level 요구사항과 데이터 소스는 매니저가 제공한다. 특정 도구, 자료 종류나 평가 기준을 제안하거나 강제하지 않는다. 서술형 평가는 매니저의 판단을 돕는 참고 의견으로 제안할 수 있다. 점수와 등급은 산정, 추천하거나 보정하지 않는다.

## 실행 책임

메인 에이전트는 오케스트레이션만 한다. 소스 탐색·원문 수집·수집 검증·목표별 그룹핑·그룹핑 검증·MD 초안·초안 검증을 별도 역할에 배정하고 진행 상태, 인간 확인 gate와 교차검증 결과를 취합한다. 원문 수집은 실행 환경의 latest fast-tier, 그룹핑과 초안은 서로 다른 latest top-tier 에이전트가 담당한다. 메인은 원문 수집, 그룹핑, 초안 작성이나 직접 사실 검증을 하지 않는다. 후속 수정, 최종본 변환과 readback도 위임한다.

착수 소스 탐색 전에 [위임 조사와 독립 검증](references/research-verification.md)을 읽고 역할, 실제 사용 모델명, 수집 manifest와 반복 검증 절차를 따른다. 필요한 도구·tier·독립 agents가 없으면 제한을 인간에게 정확히 보고하고 변경 허용 없이 우회하지 않는다. 아래 작성·검증 지침은 배정된 역할이 수행한다.

## 1. 조사 착수: 기간과 입력을 매니저에게 확인

- 대상 팀, 팀원과 현재 Job Level을 확인한다. 팀의 연간 목표 또는 분기 목표와 각 레벨의 요구사항을 요청한다. 제공받은 목표에 맞춰 조사와 서술의 방향을 정한다.
- 회사나 팀이 정의한 Job Level과 기대치를 우선 사용한다. 정의가 없으면 매니저와 현재 수준 및 다음 수준의 기대치를 논의해 확인한 뒤 조사에 착수한다. 팀원의 현재 레벨이나 기대치를 임의로 정하지 않는다. 이번 평가를 위해 합의한 기대치를 회사의 공식 Job Level 정책으로 표현하지 않는다.
- “1분기”, “이번 분기”, “몇 월” 등의 표현은 정확한 날짜 범위로 제안한다. 연도, 달력 분기와 회계 분기의 구분, 필요한 경우 시간대를 명시하고 매니저에게 확인한다. 월말과 윤년을 검사하고 자료 조회의 종료 경계가 마지막 날을 포함하는지 확인한다.
- “지난 N 분기”가 특정 분기인지 여러 분기인지 불분명하면 해석과 날짜 범위를 함께 제안하고 확인한다. 기준 연도나 기간을 추정한 경우 추정임을 표시한다.
- 제공받은 데이터 소스별로 읽기 전용 탐색을 서브 에이전트에 맡긴다. 전체 조사 전에 실제 위치와 대략적인 내용을 확인하고 매니저에게 다시 제시한다.
- Jira가 제공되면 실제 project 이름과 key, Notion 페이지가 제공되면 페이지 제목과 요약 및 관련 하위 블록이나 페이지, Slack 채널이 제공되면 실제 채널 이름을 확인해 제시한다. 이는 제공된 소스를 확인하는 예시이며 필수 소스 목록이 아니다.
- Jira 등 업무 관리 도구가 자료로 제공되면 티켓에서 GitHub 연동 정보나 PR·커밋 링크를 확인한다. 코드베이스 확인이 필요하면 관련 GitHub 저장소와 조회 범위를 착수 확인에 포함한다. 연동되어 있다고 가정하지 않는다.
- 확인한 링크와 식별자만 사용한다. 접근 실패, 잘못된 링크, 필요한 자료의 누락은 발견한 상태 그대로 알린다.
- 소스별 기간 적용 날짜, 팀원 identity/alias와 collaborator 매칭 규칙도 확인한다.
- 기간, 대상자, 데이터 소스 범위, 팀 목표와 요구사항을 한 번에 정리해 착수 확인을 받는다. 이미 구체적으로 확인한 항목은 다시 승인받지 않는다. 다른 항목이 확정되어도 필수 입력의 누락을 임의로 메우지 않는다.
- 독립된 서브 에이전트 검증을 사용할 수 없는 환경이라면 그 한계를 알리고 대체 방식을 합의한 뒤 진행한다. 같은 에이전트의 재독을 독립 검증으로 표현하지 않는다.

## 2. 조사 진행: 수집 → 그룹핑 → 초안과 단계별 검증

착수 확인 후에는 범위 안의 조사 진행에 매니저의 단계별 확인을 요구하지 않는다. [위임 조사와 독립 검증](references/research-verification.md)에 따라 fast-tier 수집자가 확인된 범위의 원문 전체를 로컬 임시 파일에 수집하고 별도 검증자가 범위를 검증한다. Jira라면 티켓 본문·메타데이터와 모든 코멘트 원문까지 포함하며 페이지 순서·건수·누락은 manifest에 남긴다. 부분 수집을 전체 완료로 보고하지 않는다.

코드베이스 확인이 필요한 경우 Jira 등 업무 관리 도구의 티켓을 출발점으로 GitHub 조사를 수집 역할에 배정한다. 티켓과 연결된 PR·커밋 및 관련 코드를 확인하며, [티켓 기반 GitHub 조사](references/research-verification.md#티켓-기반-github-조사)의 범위와 근거 수집 절차를 따른다.

별도 top-tier 에이전트가 검증된 원문을 팀 연간·분기 목표별로 묶되 업무 흐름과 개인 기여의 세부사항을 유지한다. 이를 독립 검증한 뒤, 그룹핑 작성자와 다른 top-tier 에이전트가 MD 초안을 작성하고 별도 검증자가 원문과 대조한다. 지적은 해당 작성자에게 수정 재배정하고 영향을 받은 부분을 다시 검증한다.

미확인·충돌 내용은 평가 근거에서 제외하되 확인된 근거로 초안은 계속 작성한다. 실제 확보한 근거 링크와 확인 질문을 매니저에게 전달한다. 팀 목표에 억지 귀속하거나 팀 성과를 개인에게 귀속하지 않으며 자료 부재를 기대 수준 미달의 근거로 삼지 않는다.

## 3. Markdown 초안: 사실 검토와 참고 의견

- 개인별 초안을 MD 파일로 작성한다. 저장 위치는 매니저가 지정한 작업 위치를 사용한다. 개인별 자료와 결과를 스킬 저장소에 넣지 않는다.
- 매니저가 별도 초안 구성을 지정하지 않으면 `성과`, `역량`, `기술기여` 세 항목을 기본 템플릿으로 사용한다. 각 항목에서 확인된 사실과 근거, 서술형 참고평가, 확인 질문을 구분한다.
- `성과`: 확인된 업무 결과와 개인의 기여를 팀 목표와 연결해 평가한다.
- `역량`: 확인된 행동·개인 기여와 제공된 Job Level 요구사항을 근거로 역량 측면의 서술형 참고평가를 작성한다. 현재 기대 수준의 충족 여부와 성장에 필요한 부분을 근거로 설명하며, 역량 이름이나 관련 활동을 나열하는 데 그치지 않는다.
- `기술기여`: 설계·구현·리뷰 등 확인된 기술 기여와 개인의 역할을 근거로 평가한다. 코드베이스 확인이 필요하면 티켓 기반 GitHub 조사 결과를 사용한다.
- 초안에는 확인된 업무와 개인의 기여, 팀 목표와의 관련성, 각 서술을 뒷받침하는 근거 링크를 담는다. 제공된 목표나 요구사항과 연결되지 않는 내용에 연결 관계를 만들어내지 않는다.
- 현재 Job Level에서 기대하는 수준에 부합하는지, 기대 수준에 못 미치는 부분이 있는지 근거에 기반한 참고 코멘트를 작성한다. 다음 Job Level을 위해 더 보여줘야 할 역량도 제공된 요구사항에 따라 제안한다. 레벨별 요구사항 자체를 만들어내지 않는다.
- 사실, 매니저가 제공한 판단, 에이전트의 서술형 참고 의견과 확인 질문을 구분한다. 참고 의견이 확정된 평가나 승진 판단으로 보이지 않게 표시한다.
- 각 매니저 확인 질문 아래에 해당 항목의 조사 컨텍스트를 토글로 제공한다. 매니저가 업무 배경·흐름, 개인 역할, 확인된 사실과 미확인 사항, 실제 근거 및 답변의 영향을 열어보고 답변하도록 안내한다. Markdown 초안의 형식과 작성·검증 기준은 [매니저 확인 질문과 조사 컨텍스트](references/manager-corrections.md#매니저-확인-질문과-조사-컨텍스트)를 따른다.
- 매니저가 각 항목에 대해 실제로 있었던 일인지와 개인의 역할을 검토하도록 안내한다. 직접 MD를 수정하거나 대화 인터뷰로 정정할 수 있다.
- 직접 수정이 있을 수 있으므로 파일을 다시 읽고 이전 초안과 비교한 뒤 후속 수정을 한다. 매니저의 수정 내용을 덮어쓰지 않는다.
- outer loop는 [매니저 수정과 메모리](references/manager-corrections.md)에 따라 반영한다. 개인별 사실 정정은 해당 회차 기록으로 남기고, 장기 메모리에는 작성 선호와 면담 순서만 저장한다.
- 매니저가 초안 검토를 마쳤다는 확인을 받은 뒤 최종본 단계로 진행한다. 해결하지 못한 질문은 확인된 사실로 바꾸지 않는다.

## 4. 최종본: 매니저 포맷과 저장 방식

- 매니저가 전달한 최종 포맷에 맞춰 개인별 최종 평가서를 작성한다. 포맷이 없으면 전달받고, 고정된 공식 양식을 임의로 적용하지 않는다.
- 참고 코멘트, 근거와 확인 질문이 최종 포맷에서 어떻게 취급되어야 하는지는 매니저의 요구에 맞춘다. 내부 검토 내용을 팀원 전달용이나 제출본에 자동으로 포함하지 않는다.
- 매니저의 Notion 또는 문서 관리 시스템에서 private 데이터베이스나 페이지로 관리하는 방식을 선택적으로 권장한다. 매니저가 원하지 않으면 넘어간다.
- 실제 생성이나 저장은 매니저가 선택한 위치와 현재 요청의 허용 범위 안에서 수행한다. private로 저장할 때는 실제 권한을 확인하며, 페이지 이름이나 데이터베이스의 private 표기를 권한 보장으로 간주하지 않는다. 확인할 수 없으면 한계를 밝히고 저장 방법을 정한다.
- 저장 후 내용을 다시 읽어 최종 포맷과 내용이 반영되었는지 확인한다. HR, CTO나 CEO의 확인 또는 제출이 완료되었다는 상태는 실제 확인 없이 표시하지 않는다.
- 면담에 사용할 버전과 제출본을 구분한다. 면담에서 나온 정정은 매니저가 검토해 반영한 뒤 제출본으로 관리한다.
